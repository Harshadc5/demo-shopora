Part 1 — Approach and philosophy
The core idea: URL-parameter-driven demo scenarios
You are NOT building a real e-commerce backend. You are building 25 deterministic page states that render on demand when a specific URL is loaded. Each scenario has a URL like /cart.html?demo=stacked-discounts, and when that URL loads, JavaScript detects the demo parameter and renders that specific scenario's UI state.
This means: no login system, no real promo engine, no real inventory. Everything is static configuration + JavaScript that reads the URL parameter and paints the right state onto the page. The tag then observes that state exactly as if it were a real retailer's page.
Why this approach
Deterministic — every scenario renders the same way, every time. Demo reliability is critical.
No backend — you don't have time to build a full e-commerce backend, and it's not needed for the demo to work.
Testable — you can navigate to each URL and visually verify the scenario before the tag ever runs.
Reproducible — the demo lead can navigate to any scenario on demand during a customer conversation.
What Shopora looks like today (baseline)
Shopora currently has: homepage (/index.html), category page (/category.html with ?category= param), cart page (/cart.html), checkout page (/checkout.html), and orders page (/orders.html). Categories: Electronics, Fashion, Home, Books. Free delivery threshold: $35. Loyalty tier mentioned: 'Shopora Plus — extra 5% off.' Currency: USD.
Existing brand landscape (from tag test logs): VoltMax, PulseTune, Luna, MetroStride, OakLine. This doc expands the catalog and specifies where each brand appears.

2.5 — Demo mode URL routing infrastructure
Build a small JavaScript module (e.g., /public/js/demo_router.js) that reads URL parameters on every page load and applies the appropriate demo state. Include this script on every page.
The router reads three main parameter types:
• 
?demo=&lt;scenario-slug&gt; — triggers a specific scenario's state (e.g., ?demo=stacked-discounts).
• 
?identity=&lt;state&gt; — sets identity state (guest | logged-in). Default: guest.
• 
?member_tier=&lt;tier&gt; — sets loyalty tier when logged in (member | plus | gold). Default: none.
The router modifies the DOM after page load. All 25 scenarios below map to a specific combination of these parameters. Each scenario section below specifies its exact URL.
// Pseudocode for /public/js/demo_router.js
document.addEventListener("DOMContentLoaded", () =&gt; {
  const params = new URLSearchParams(window.location.search);
  const demo = params.get("demo");
  const identity = params.get("identity") || "guest";
  const memberTier = params.get("member_tier");
  
  // Apply identity state
  if (identity === "logged-in") applyLoggedInState(memberTier);
  
  // Apply demo scenario
  if (demo) applyDemoScenario(demo);
});
function applyDemoScenario(slug) {
  const handler = DEMO_HANDLERS[slug];
  if (handler) handler();
  else console.warn("Unknown demo scenario:", slug);
}
const DEMO_HANDLERS = {
  "stacked-discounts": () =&gt; { /* populate cart with 3 stacked promos */ },
  "hero-claim-mismatch": () =&gt; { /* set hero to promise 35% off */ },
  "brand-dominance-trending": () =&gt; { /* make trending row 60% VoltMax */ },
  // ... 22 more handlers, one per scenario
};
2.6 — Cart state management for demo
For scenarios that need pre-populated carts, the demo router should populate the cart state directly (via sessionStorage or a JS object) rather than requiring the user to add items manually. This makes each cart scenario deterministic.
// Example: ?demo=stacked-discounts should populate the cart
// with 1x el-2 PulseTune Headphones, apply WELCOME10 code,
// apply member 5% discount, show all three in savings breakdown.
function populateStackedDiscountsCart() {
  const cartState = {
    items: [
      { sku: "el-2", quantity: 1, unit_price: 89.99, name: "PulseTune Headphones" }
    ],
    subtotal: 89.99,
    savings_components: [
      { label: "Markdown", amount: 30.00 },
      { label: "WELCOME10 code (10%)", amount: 6.00 },
      { label: "Shopora Plus (5%)", amount: 2.70 }
    ],
    shipping: 0,
    total: 51.29
  };
  renderCart(cartState);
}
2.7 — Add data attributes for tag observation
The tag identifies elements by data attributes. For every scenario, make sure the following data attributes are present on the appropriate elements:
On the body element:
• 
data-page-type: homepage | category | cart | checkout | pdp | search | confirmation
On product cards:
• 
data-product-id: SKU
• 
data-brand: brand name
• 
data-category: electronics | fashion | home | books
• 
data-sponsored: true | false
• 
data-availability: in-stock | out-of-stock | low-stock
• 
data-position: numeric position within surface
On modules (banners, hero, promo):
• 
data-module-type: hero | banner | promo | carousel | brand_band | countdown
• 
data-module-id: unique ID for the module instance
On the header account chip:
• 
data-identity-state: guest | recognized
• 
data-member-tier: (only when recognized)
• 
data-customer-hash: (only when recognized; use a demo placeholder value)
On cart lines and promo field:
• 
data-cart-item-sku, data-cart-item-quantity, data-cart-item-line-total
• 
data-promo-state, data-applied-code, data-inline-reason

  ·  
Stacked discounts below margin floor
Pattern: Ungoverned Offer Stacking
Trigger URL:
/cart.html?demo=margin-floor-violation&amp;identity=logged-in&amp;member_tier=plus
What should render:
Cart has 1x MetroStride Running Shoes (fa-3, listed $74.99, marked from $94.99 — 21% off). Apply SAVE20 code (20% off = -$15). Plus loyalty 5% (-$3.75). Plus $10 sale credit. Effective price: $46.24. Part 4 — Testing and handoff checklist
4.1 — Per-scenario verification
For each of the 25 scenarios, run through this checklist before marking it complete:
1. 
Navigate to the trigger URL. Does the page render without errors (check DevTools console)?
2. 
Does the page visually display what the scenario spec says it should? (Take a screenshot.)
3. 
Do all required data attributes exist on the required elements? (Inspect in DevTools.)
4. 
Run the tag against the page. Does the tag emit all expected signals? (Check the payload.)
5. 
Save the trigger URL, screenshot, and captured payload to a test log for the scenario.
4.2 — Cross-scenario verification
1. 
Confirm all 25 URLs load successfully without JavaScript errors.
2. 
Confirm the tag captures the correct page_type for each scenario URL.
3. 
Confirm session_id is visit-stable — navigate through a multi-step scenario (like 4.1 category → PDP) and confirm the same session_id appears on both captures.
4. 
Run a quick smoke test on each of the four base pages (/index, /category, /cart, /checkout) WITHOUT demo params to confirm baseline Shopora behavior wasn't broken by the demo router.
4.3 — Handoff criteria to the scanner team
When you're ready to hand this off to the scanner + policy engine team, package the following:
• 
The 25 trigger URLs, labeled by scenario ID.
• 
A test log with, for each scenario: the URL, a screenshot of the rendered page, and the raw JSON payload the tag captured.
• 
Any deviations from this spec you made and why (e.g., 'used $39.30 instead of $39.99 for margin floor scenario because floating-point comparison').
• 
A short (1-page) note on what you found confusing or ambiguous in this spec, so it can be improved for the next hand-off.
4.4 — What to bring to RC and the advisor
Once you complete Part 2 (foundation) and any 3 scenarios, schedule a review before continuing. RC or Sravan should confirm:
• 
Foundation is solid before you build 22 more scenarios on top of it.
• 
The 3 scenarios you built match the intent (not just the literal spec) — sometimes intent is unclear and worth catching early.
• 
The data attributes you're using match what the tag actually looks for.
Don't build all 25 in one go without a review checkpoint. If you build 25 scenarios with the wrong data attributes, that's 25 things to fix. If you build 3 with wrong attributes, that's 3 things to fix plus a corrected pattern for the remaining 22.
